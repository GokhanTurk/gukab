# Release process

A release is **one commit**, and the tag goes on top of it. Commit message format:
`vX.Y.Z: <summary of the changes>` (see `git log`). Do **not** add a separate
`docs: ...` commit and tag that — the GitHub Actions run name is derived from the head
commit message, so the release would show up under the docs message.

## What goes into the single release commit

- `Cargo.toml` + `Cargo.lock` version bump
- `CHANGELOG.md` new section — cargo-dist takes the release **body** from here; the
  **title** it generates from version + date (`1.9.0 - 2026-08-10`)
- `README.md` / `docs/dev/*.md` / `examples/*.toml` if behavior changed
- `docs/demo.gif` — the TUI banner prints `v{CARGO_PKG_VERSION}`, so the GIF goes stale
  every release. Re-record from the repo root:
  `cargo build --release && vhs docs/demo.tape`
  (needs `vhs` + FiraCode Nerd Font; the tape copies its fixture home from
  `docs/demo-home/` to `/tmp`)

## Tag and CI

```bash
git tag vX.Y.Z          # lightweight
git push origin main --tags
```

Pushing the tag triggers the cargo-dist **Release** workflow
([.github/workflows/release.yml](../../.github/workflows/release.yml), autogenerated by
`dist init` — edit [dist-workspace.toml](../../dist-workspace.toml), not the workflow).
It builds four targets (linux-gnu x86_64, windows-msvc x86_64, darwin aarch64 + x86_64),
shell + powershell installers, and the `gukab-update` self-updater, and installs to
`~/.local/bin`.

**Follow the workflow to completion** — it takes ~5-7 min:

```bash
gh run watch <id> --exit-status    # run in the background, it is long
gh run list && gh run view <id>    # verify afterwards
```

The user's installed client updates via `gukab-update`, which depends on the artifacts
actually being published. "CI started" is not delivery: if CI fails the release is
stranded and the user waits without noticing. Report success (artifacts published) or
failure (which job broke, where).

## Windows

The maintainer develops on Linux/macOS. `#[cfg(windows)]` code is verified by
[.github/workflows/windows-check.yml](../../.github/workflows/windows-check.yml) — it runs
on the `windows-support` branch, on PRs to `main`, and via `workflow_dispatch`. Trigger it
manually when Windows-specific code changes outside a release.

## Wiki

There is a **GitHub wiki** outside the repo (`git@github.com:GokhanTurk/gukab.wiki.git`);
the README links to it as the full reference. Behavior changes should also update its
Configuration / Keybindings / Serial-Console / Home pages.

## Distribution is not yours to do

Never touch the installed `~/.local/bin/gukab` binary (no copy / `install` / delete). Work
only inside the repo; `target/` is enough for builds. The user distributes by pushing to
GitHub and running `gukab-update` themselves. If a fix needs to be seen "live", build
release and point at `target/release/gukab`.
